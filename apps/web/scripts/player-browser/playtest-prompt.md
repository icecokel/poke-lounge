# Poke Lounge 플레이어 관점 반복 테스트·버그 수정 프롬프트

실행 흐름: **직접 플레이 → 버그 기록 → 수정·검증 → 커밋·푸시 → 새 회차**

완료 기준은 **새 브라우저·새 방으로 시작하는 유효한 전체 플레이 5회**다. 아래 프롬프트를 새 작업에 붙여 넣어 사용한다.

```text
@poke-lounge-remote-mcp

Poke Lounge를 실제 플레이어 관점에서 로컬 플레이 테스트하고,
발견한 버그를 수정·검증·커밋·푸시하는 작업을 반복한다.

단순히 테스트 코드를 통과시키는 것이 아니라,
직접 브라우저 화면을 보며 게임을 플레이하고 문제를 찾아 개선하는 작업이다.

────────────────────
1. 작업 목표와 종료 조건
────────────────────

유효한 전체 플레이 테스트를 5회 완료한다.

1회는 다음 전체 과정이다.

새 브라우저 세션·새 방 생성
→ 대기실 준비
→ 스타터 선택
→ 중앙 집결·출발
→ 1라운드 탐험·토너먼트
→ 2라운드 탐험·토너먼트
→ 3라운드 탐험·토너먼트
→ 최종 순위·점수 확인
→ 게임 화면의 ‘방 나가기’
→ 입장 화면 복귀 확인

전투 한 번, 토너먼트 한 번, 라운드 하나를 1회로 세지 않는다.
이전 작업의 테스트 결과를 이번 5회에 합산하지 않는다.
연속 2회 버그가 없더라도 조기 종료하지 않는다.

5회 완주 후에도 마지막 회차에서 발견한 수정 대상 버그는
수정·재검증과 기록까지 마친 뒤 최종 보고한다.

────────────────────
2. 반드시 실제 플레이어처럼 진행
────────────────────

Playwright로 실제 브라우저를 열고 아래 과정을 반복한다.

현재 스크린샷을 실제로 확인
→ 화면에 보이는 정보로 다음 행동 판단
→ 클릭·탭·키보드·드래그로 한 행동 수행
→ 변경된 화면 확인

Playwright는 입력 전달 수단이다.
무엇을 할지는 에이전트가 현재 화면을 보고 결정한다.

랜덤 인카운트, 상대 포켓몬, HP, 기술, 보유 아이템, 자금,
남은 시간에 맞춰 행동을 바꾼다.
사전에 정한 공격이나 이동을 무조건 반복하지 않는다.

허용:
- 실제 버튼 클릭·탭
- 입력란 작성
- 키보드 이동·선택·확인
- 조이스틱 드래그와 화면 스크롤
- 보이는 UI의 접근성 이름·문구를 이용한 조작 보조

금지:
- 전체 플레이를 자동으로 수행하는 spec·자동 의사결정 루프
- 게임 API 직접 호출로 공격·포획·구매·준비·승리 처리
- 게임 스토어·localStorage·DB·Redis·E2E getter를 읽어 플레이 판단
- 정적 지도·기술·종족 데이터 파일을 읽어 공략 결정
- HP·아이템·경험치·포획·승리 결과 주입
- 시간 가속·시계 정지·서버 제한시간 변경
- 가려진 버튼 강제 클릭, 비활성 버튼 우회
- 스크린샷 파일명이나 Base64 문자열만 보고 화면을 확인했다고 처리

버그 발견 후 원인 분석을 위해 제품 소스를 읽는 것은 허용한다.
소스 분석·단위 테스트와 실제 플레이는 명확히 분리한다.

────────────────────
3. 시작 전 사전 점검
────────────────────

현재 브랜치·커밋·원격 저장소·미커밋 변경을 확인한다.
기존 다른 작업의 변경은 임의로 되돌리거나 함께 커밋하지 않는다.

다음 지침을 먼저 읽고 현재 구현과 사용법을 확인한다.
- .agents/skills/poke-lounge-agent-browser-test/SKILL.md
- apps/web/scripts/player-browser/README.md
- README.md

로컬 프로덕션 빌드와 격리된 실제 API·PostgreSQL·Redis·워커를 사용한다.
모의 응답이나 테스트용 게임 상태 주입은 사용하지 않는다.
다른 작업의 서버·컨테이너·브라우저는 건드리지 않는다.

게임 시간을 시작하기 전에 다음 경로를 먼저 검증한다.

브라우저 열기
→ 이미지 캡처
→ 이미지 수신
→ 실제 이미지 뷰어로 확인
→ 안전한 UI 조작
→ 변경 화면 확인

이 경로가 정상 동작하지 않으면 게임부터 시작하지 않는다.
먼저 테스트 도구 문제를 해결한다.

이미지 확인 기록은 실제 이미지를 본 뒤에 작성한다.
프레임 ID·해시를 자동 복사하는 것으로 시각적 확인을 대신하지 않는다.

────────────────────
4. 매회 플레이 목표
────────────────────

각 회차에서 아래 목표를 모두 달성하도록 플레이한다.

A. 종합 우승을 최대한 노린다.
상황에 맞게 육성·포획·회복·아이템·기술·교체를 선택한다.
단순히 대회 시간이 끝나기를 기다리거나
제한시간 초과 기본 행동에 맡기지 않는다.

B. 포획에 최소 3회 성공한다.
스타터는 제외한다.
몬스터볼 사용 횟수가 아니라 실제 파티 또는 PC 합류까지 확인한다.
3라운드 전체를 합친 횟수다.

C. 상점 거래를 최소 1회 완료한다.
화면에서 구매 가능한 상품들을 확인한 뒤 그중 하나를 무작위로 고른다.
금액 차감과 아이템 수량 증가까지 화면에서 확인한다.
돈이 부족하면 정상 플레이로 자금을 확보한다.

D. 최종 결과를 확인하고 UI로 퇴장한다.
라운드 우승자·누적 순위·최종 점수의 표시를 확인한다.
퇴장 후 입장 화면 복귀와 조작 가능 여부도 확인한다.

우승 실패·정상적인 포획 실패·자금 부족 자체는 버그가 아니다.
패배한 결과를 숨기거나 우승한 것으로 바꾸지 않는다.

완주와 목표 달성을 구분한다.
예: ‘3라운드 완주 / 준우승 / 포획 2회 / 구매 1회 / 포획 목표 미달’.

────────────────────
5. 플레이하면서 검사할 사항
────────────────────

단순히 버튼이 눌리는지에 그치지 말고 다음을 살핀다.

- UI/UX:
  조작 방법을 알아볼 수 있는지, 화면이 잘리거나 겹치는지,
  활성·비활성 상태와 제한 이유가 명확한지.

- 전투:
  공격·아이템·교체·도주 흐름, 선두 전투불능 후 강제 교체,
  HP·PP·상태이상·결과 문구, 기술 습득·진화 연출.

- 데이터 보존:
  포획·아이템 사용·구매·경험치·화폐가 실제 화면에 반영되는지,
  집결이나 라운드 전환 직전의 확정 결과가 유실·중복되지 않는지.

- 대회 진행:
  준비·출발·대진·관전·다음 라운드 전환,
  본인 위치·상대·순위 표시, 컨페티와 최종 종료 상태.

확인되지 않은 현상은 ‘의심’ 또는 ‘추가 재현 필요’로 기록한다.
추측만으로 원인을 확정하거나 게임 밸런스를 변경하지 않는다.

────────────────────
6. 버그 발견 후 수정 루프
────────────────────

버그를 발견하면 먼저 아래를 기록한다.

버그 ID / 심각도 / 검사 커밋 / 회차·라운드 /
직전 행동 / 재현 절차 / 기대 결과 / 실제 결과 /
스크린샷·입력 기록 / 재현 여부

진행 가능한 경미한 문제는 기록하고 회차를 끝낸 뒤 수정한다.

진행 불가·결과 유실 등 중대한 문제는 증거를 확보하고,
해당 회차를 ‘중단’으로 기록한 뒤 수정한다.
중단된 회차는 5회 완주 카운트에 넣지 않는다.

수정 절차:
화면 증거 확인
→ 관련 코드 분석
→ 가능한 경우 수정 전 실패 회귀 테스트 작성
→ 최소 범위 수정
→ 타입·린트·관련 테스트 검증
→ 수정본을 다시 빌드
→ 실제 UI에서 재현 절차를 다시 수행
→ 의미 단위로 커밋·푸시
→ 새 방에서 다음 회차

단위 테스트 통과만으로 실제 UI 재검증을 대신하지 않는다.
테스트를 통과시키기 위해 기대 결과를 낮추거나
포획률·보상·AI·타이머를 유리하게 바꾸지 않는다.

수정 범위가 테스트 도구인지 제품 버그인지 구분해 기록한다.
원인을 재현하지 못했거나 수정 효과를 확인하지 못한 항목은
‘수정 완료’로 표시하지 않는다.

현재 작업 브랜치와 원격을 확인한 뒤 검증된 변경만 푸시한다.
강제 푸시·무단 이력 재작성·검증 우회는 하지 않는다.
푸시 성공과 CI 성공, 운영 배포 완료를 구분한다.

────────────────────
7. 조작 공백·도구 실패 처리
────────────────────

게임 타이머가 진행되는 동안 불필요하게 긴 로그 조회,
문서 편집, 도구 재설정을 끼워 넣지 않는다.
가능한 사전 준비는 회차 시작 전에 마친다.

오래된 화면은 새로 확인한 뒤 조작한다.
입력 결과가 불명확하면 같은 입력을 무조건 반복하지 않는다.

문제가 생기면 다음을 따로 확인한다.
- 명령 실행 자체의 실패
- 버튼 조작 실패
- 이미지 캡처 실패
- 이미지 전달·표시 실패
- 게임 진행 불가
- 에이전트의 관찰·판단 지연

명령이 성공하고 화면 파일도 생성됐는데
이를 근거 없이 ‘Playwright가 멈췄다’고 보고하지 않는다.

관찰하지 못한 채 서버 기본 행동으로 진행된 긴 구간은
직접 플레이 실적으로 인정하지 않는다.
단순히 마지막 결과 화면만 열어 완주 횟수를 채우지 않는다.

도구 문제가 복구되면 새로 시작하거나,
실제로 확인 가능한 지점부터 제한사항을 명시해 재검증한다.
복구 불가능한 외부 장애라면 구체적인 명령·응답·시각·복구 시도와
남은 작업을 기록하고 안전하게 종료한다.
무조건 성공이나 5회 완료를 주장하지 않는다.

────────────────────
8. 문서·카운팅·최종 보고
────────────────────

시작 시 docs/ 아래에 이번 실행 전용 원장을 만든다.
이전 문서를 덮어쓰거나 이전 실적을 합산하지 않는다.

‘시도 횟수 / 유효 완주 횟수 / 목표 달성 횟수’를 따로 관리한다.
각 회차 종료 또는 중단 직후 갱신한다.

회차별 기록:
- 브라우저·화면 크기·검사 커밋
- 시작·종료 시각
- 라운드별 성적과 최종 순위·점수
- 포획 성공 수와 확인한 포켓몬
- 구매 상품·구매 전후 금액·수량
- 발견한 버그 ID
- 수정 내용·재검증 결과·커밋
- 관찰 공백·시간 초과 기본 행동·미검증 범위

스크린샷·입력 로그·검증 로그는 output/에 보존한다.
비밀번호·세션 식별자 등 민감한 값은 마스킹한다.
docs/·output/·Output/의 기존 Git 제외 정책을 유지한다.

최종 보고에는 다음을 포함한다.
1. 유효 완주 횟수와 회차별 목표 달성 결과
2. 발견·수정·미해결 버그
3. 실제 UI 재검증과 자동 회귀 테스트를 구분한 결과
4. 커밋·푸시·CI 상태
5. 브라우저·전용 서버 정리 결과와 남은 미커밋 변경

실제 휴대폰에서 검사하지 않았다면
Safari·Chrome·카카오톡 앱 실기기 테스트 완료라고 말하지 않는다.

계획이나 문서 작성만으로 끝내지 말고,
사전 점검부터 실제 플레이·수정·재검증을 실행한다.
```
