# Poke Lounge

Poke Lounge는 같은 마을에서 포켓몬을 탐색·포획·육성하고 3라운드 챔피언십을 진행하는 브라우저형 비공식 Pokémon 팬 게임이다.

구현 대조: `13f230f`와 현재 작업 트리 · 2026-10-11 KST. 아래는 소스 기준의 현재 구현을 설명하며, 모든 조합이나 실기기 환경의 검증 완료를 뜻하지 않는다.

### 라운드 시작 규칙

첫 방장 시작은 바로 탐험 시간을 시작하지 않는다.

```text
대기실 준비 → 방장 시작 → 스타터/파티 준비 → 필드 렌더링·중앙 집결
→ 사람·AI 전원 준비 → 3 → 2 → 1 → 탐험 시작
```

이 경로에서는 `startRoom()` 직후 시작·종료 시각이 `null`이고, 전원 준비 후 서버가 3초 미래의 공통 시작 시각을 설정한다. 선택·로딩·카운트다운 시간은 탐험 시간에서 차감하지 않는다.

정상 **2·3라운드 전환도 필드 준비와 카운트다운을 거친다.** 앞 토너먼트 완료 후 5초간 결과를 표시하고, 다음 라운드의 시작·종료 시각을 `null`로 두고 전원의 준비를 다시 받는다. 스타터는 재선택하지 않으며 중앙 출발 위치로 복귀한다. 사람·AI 전원의 연결·구독·파티·준비가 완료되면 서버가 3초 미래의 공통 시작 시각을 설정한다. 참가자가 2명 미만이라는 이유만으로 대기실로 돌아가는 분기는 없으며, 연결된 사람이 없으면 방을 닫는다.

토너먼트 시드는 매 라운드 서버가 무작위로 배정한다. 입장 순서나 사람·AI 여부와 무관하며, 클라이언트는 서버가 확정한 대진을 받기 전까지 "대진 확정 대기"를 표시한다.

### 점수·전투 진행

- 각 토너먼트가 끝나면 순위 점수를 3라운드 동안 합산한다. 우승 100점, 준우승 70점, 공동 3위 45점, 공동 5위 15점이다. 같은 단계에서 탈락하면 같은 점수이며, 남은 HP와 파티 수는 점수에 영향을 주지 않는다. 누적 동점은 공동 순위다.
- 야생 격파 경험치는 기본 계산 결과의 5배를 기준 보상으로 삼는다. 90초는 선두와 대기 팀원이 각각 기준 보상의 250%, 3분은 선두 200%·대기 팀원 각각 150%, 5분은 선두 125%·대기 팀원 각각 100%를 받는다. 현재 4세대 전투에서 전투불능 포켓몬은 경험치를 받지 않는다.
- 토너먼트는 쓰러뜨린 상대의 기본 격파 경험치(5배)를 경기 종료 후 지급한다. 승패와 관계없이 출전한 포켓몬들에게 균등 분배하며 전투불능 포켓몬도 받는다. 경기 중에는 레벨·능력치를 바꾸지 않고, 종료 후 레벨업과 기술 습득을 다음 경기에 반영한다. 다음 경기 배정은 종료 확정부터 최대 25초 기다리며, 선택하지 않은 기술은 배우지 않는다. 시작한 경기의 기술은 도중에 변경하지 않는다. 토너먼트 보상에는 탐험 시간별 추가 배율·파티 공유율을 적용하지 않으며 진화는 기존 야생전 성장 흐름에서 처리한다.
- 탐험 종료 시 미완료 기술 선택은 화면을 유지한다. 기술 선택 전체에 25초 제한을 적용하고, 결과를 저장한 뒤 준비 완료를 전송한다. 다른 참가자는 준비 완료를 기다리며, 탐험 종료 후 최대 25초가 지나면 서버가 저장된 파티로 토너먼트를 진행한다.
- 일반 전투 메시지는 300ms(0.3초) 간격으로 자동 진행한다. 모바일 일반 메시지에는 ‘다음’ 버튼을 표시하지 않으며, 결과·기술 습득의 ‘확인’ 버튼은 유지한다. 데스크톱 확인 입력·메시지 클릭으로 기다리지 않고 넘기는 동작과 메시지박스 위치는 그대로다. 전투 연출 중에는 메시지 진행과 입력을 잠그고, 결과·기술 습득 확인은 자동으로 넘기지 않는다.
- 게임 메시지의 동적 이름·기술·아이템·능력치 뒤 조사는 `es-hangul`로 받침에 맞게 붙인다. 예: `파이리의 방어가 떨어졌다!`, `피카츄를 잡았다!`, `마릴과 파티 포켓몬을 교체했다.`. 레벨과 이름 끝의 숫자는 한글 발음으로 조사를 선택하며 숫자 표시는 유지한다. 영어·일본어는 해당 언어의 문장으로 번역한다.
- AI는 타입 상성·물리/특수 능력치·능력치 변화·화상·명중률·고정 피해를 고려해 공격한다. 서버 대전에서는 강제 교체 시 상성을 비교하고, 위험이 뚜렷하게 줄어드는 경우 자발적으로 교체한다. 다중 턴 예측·특성·날씨까지 시뮬레이션하는 전략 AI는 아니다.

점수 규칙 변경 전 방의 누적 점수는 소급 재계산하지 않는다. 배포 후에는 새 방에서 시작해야 세 라운드 모두 같은 기준을 적용한다.

### 전투 상대 파티 표시

트레이너전·토너먼트에서는 상대 HP 패널 바로 아래에 참가 파티 수만큼 몬스터볼과 `남은 수/전체 수`를 표시한다. 현재 출전 포켓몬도 남은 수에 포함하고, 전투불능 슬롯은 회색·× 표시로 자리를 유지한다. 현재 출전 슬롯은 밑줄로 구분한다. 상대 HP가 화면에서 0으로 내려가는 시점에 숫자를 갱신하며, 미공개 종족·기술·대기 포켓몬의 HP는 이 표시줄에 노출하지 않는다. 모바일·웹 모두 기술 선택 중에도 표시하고, 모바일 전체화면 교체에서는 상단 전투 정보에 같은 표시를 유지한다. 야생전에서는 생략한다.

일반 아이템과 가방은 게임 화면에서 제공하지 않는다. 야생전의 몬스터볼 명령은 보유 수량 없이 사용할 수 있다.

### 결과 표시와 모바일 재접속

라운드·최종 순위는 표 구조(순위·트레이너·이번 점수·누적 점수)로 표시한다. 중간 결과는 필드와 구분되는 불투명 패널에서 세로 스크롤하며, 패널에 포커스를 두면 방향키·Space는 필드 이동 대신 결과 읽기에 사용한다. 최종 결과는 전체 작업 화면의 스크롤 본문과 별도 하단 버튼 영역을 사용한다. 좁은 화면에서는 이번 점수와 누적 점수를 한 열에 함께 표시한다. 탐험 시간은 전부 사용할 수 있으며, 종료 후 별도의 5초 집결 시간을 두고 토너먼트를 시작한다. 중간 결과 표시와 다음 라운드 출발은 위의 라운드 시작 규칙을 따른다. 최종 결과는 유지한다.

라운드 결과에서는 **이번 라운드 우승자**와 **현재 누적 순위**를 구분한다. 누적 공동 1위가 여러 명이어도 해당 라운드 준우승자를 우승으로 표시하지 않는다. 3라운드 종료 화면의 **최종 우승**만 누적 순위를 따르며, 종료된 방의 AI는 늦게 도착한 활동 정보와 관계없이 **대회 종료**로 표시한다.

모바일 방 만들기·초대 화면은 문서 전체가 스크롤되고, 필드·전투는 고정 플레이 화면을 유지한다. 입장 입력란의 포커스만으로 제목·라운드 설정을 숨기거나 폼을 재배치하지 않는다. 화면 키보드가 열려도 같은 폼을 스크롤하여 첫 탭으로 제출한다. 입장 화면과 설정의 새로고침 버튼은 문서를 다시 불러오되 저장 데이터나 참가 신원을 삭제하지 않는다. 일반 비공개 방 생성이 완료되면 생성용 URL 플래그를 제거하고, 새로고침 시 저장된 방과 실행 UUID로 복원한다. 진행 중인 야생전·미완료 선택은 복원을 보장하지 않으며 서버 시간은 계속 흐른다.

## 구조

| 경로                                  | 역할                                                          |
| ------------------------------------- | ------------------------------------------------------------- |
| `apps/web/src/components/poke-lounge` | React 화면, 입력, 연출, Rust 런타임 연결부                    |
| `apps/web/src/features/poke-lounge`   | 분리한 도메인·응용·표시 모델·어댑터                           |
| `apps/api-rust`                       | 운영 REST/WebSocket, 방·서버 권위 경기 상태                   |
| `apps/battle-worker`                  | Rust가 호출하는 TypeScript 전투 계산 워커                     |
| `apps/db`                             | PostgreSQL migration·ROM import 도구 (TypeORM CLI, 서버 아님) |
| `packages/poke-lounge-battle`         | Web/계산 워커가 공유하는 전투·대진·라운드 규칙                |

Redis는 방·경기·실시간 상태와 작업 큐를, PostgreSQL은 ROM 문서와 영속 스키마를 담당한다.

### 시간 상수

Web·TypeScript 계산 워커·레거시 API의 게임 진행·재접속·저장·표시/연출 시간은 `packages/poke-lounge-battle/src/timing.ts`에서 관리한다. `@poke-lounge/battle/timing`으로 참조하고 기존 공개 상수 경로는 재내보내기로 호환한다. `*_MS`는 밀리초, `*_SECONDS`는 초다. Rust 서버의 시간은 `apps/api-rust/src/domain.rs`에 별도로 정의되어 있다. 두 정의는 `pnpm check:rust-ts-constants`로 CI에서 대조한다. 토너먼트 전 집결과 중간 결과 표시는 양쪽 모두 각각 5초이며 탐험 시간에 포함하지 않는다. 종료 방 보관은 아래 Rust 수명 정책을 따르며, TypeScript의 기존 종료 방 보관 상수 60초와 구분한다. 경험치 배율과 파티 공유율은 `round-settings.ts`에서 라운드 시간 프리셋 기준으로 관리한다. ROM 프레임 데이터·CSS 키프레임과 플레이 테스트 도구 자체의 타임아웃은 각각의 모듈에 유지한다.

### 방 수명과 만료 처리

활성 방 수명은 탐험 시간(90초·3분·5분)과 무관하게 **방 생성 후 최대 2시간**이며 대기실은 최대 10분이다. 스타터 선택·탐험·토너먼트를 포함하며 사람·AI 활동으로 무한 연장하지 않는다. Rust 서버는 정상 완료(`completed`) 방을 최초 완료 후 15분, 폐쇄(`closed`) 방을 최초 폐쇄 후 60초 보존한다. 결과 화면을 보거나 늦게 퇴장해도 정리 기한을 연장하지 않는다. 마지막 사람이 퇴장하면 활성 방은 `closed`가 되지만 이미 완료된 방은 `completed`를 유지한다. AI 참가자·파티는 종료 문서에 남을 수 있으며 방 문서의 TTL로 정리한다.

클라이언트는 방 상태 수신이 없을 때 30초 간격으로 서버 상태를 재확인한다. 개인 대전이 끝난 관전·대기 상태와 탭 복귀도 포함한다. 서버가 해당 방의 부재를 명확히 확인한 경우 재접속을 중단하고 저장된 방 연결을 해제한 뒤 입장 화면으로 복귀한다. 일시적인 네트워크 실패·일반 404·클라이언트 시계만으로 퇴장시키지 않으며, 이미 받은 최종 결과는 정상 정리 이후에도 화면에 유지한다.

배포 전에 이미 만료·삭제된 방의 진행은 복구하지 않는다. 새 수명 정책의 전체 플레이 확인은 배포 후 새 방에서 진행한다.

## Rust 백엔드 전환

Rust 게임 서버와 TypeScript 계산 워커를 실제 프런트에 연결했다. 운영 `compose.yaml`은 Rust API와 계산 워커를 실행하며, PostgreSQL 스키마 migration과 ROM 데이터 import는 `apps/db`(TypeORM CLI 전용, NestJS 없음)가 맡는다. 웹은 Rust 백엔드만 지원한다.

로컬 개발은 `pnpm dev:rust`로 운영과 분리된 DB·Redis, Rust API, 계산 워커, 웹을 실행한다. 주소는 `http://localhost:3300/ko-KR`다. 이 명령은 웹 개발 서버에 임시 로컬 테스트 토큰을 전달하므로 입장 화면에서 테스트 모드로 시작·계속·종료할 수 있다. 토큰은 프로세스를 다시 시작할 때 새로 생성된다. 중지는 웹에서 Ctrl+C 후 `pnpm dev:rust:stop`을 사용하며 로컬 볼륨은 유지한다. 실행 구현은 `apps/api-rust/src`에 있다. 자세한 범위와 실행법은 [Rust 백엔드 문서](apps/api-rust/README.md)에 있다.

| 브랜치      | 역할                     | 작업 시작 기준 | PR 대상 |
| ----------- | ------------------------ | -------------- | ------- |
| `main`      | 기능 통합·운영 배포 기준 | 최신 원격 상태 | —       |
| `feature/*` | 개별 기능·수정·문서 작업 | 최신 `main`    | `main`  |

```text
main에서 feature/<작업명> 생성 → PR: feature/* → main → 운영 배포
```

`main`에 직접 커밋하지 않는다. 브랜치 이름은 소문자 영문과 하이픈으로 작성한다. 예: `feature/tournament-experience`, `feature/fix-room-reconnect`, `feature/branch-flow-docs`. 기능·버그 수정·문서 작업 모두 같은 흐름을 사용한다.

원격 이름은 `upstream`이다. 아래 커밋·푸시·PR 생성·병합 명령과 절차는 사용자가 해당 작업을 요청한 범위에서 실행한다.

### 새 작업 시작

먼저 `git status`로 현재 브랜치와 변경을 확인한다. 진행 중인 작업이 있으면 해당 feature 브랜치에서 마무리한다. 작업 트리가 깨끗한 상태에서 최신 `main`을 기준으로 새 브랜치를 만든다.

```bash
git status --short --branch
git fetch upstream --prune
git switch main
git pull --ff-only upstream main
git switch -c feature/room-reconnect
```

`--ff-only`가 실패하면 로컬과 원격의 차이를 확인하고 해결한다. 강제 푸시나 작업 삭제로 맞추지 않는다.

### 기능 작업과 PR

1. feature 브랜치에서 작업하고 변경 범위에 맞는 개발 확인을 수행한다. 플레이 확인이 필요하면 [플레이어 테스트 지침](PLAYER_TESTING.md)을 따른다.
2. 관련 파일만 스테이징하고 목적별로 커밋한다. 커밋 제목은 `feat: 토너먼트 경험치 지급 추가`, `fix: 방 재접속 처리 수정`, `docs: 브랜치 운영 절차 정리`처럼 작성한다.
3. 요청받은 feature 브랜치를 원격에 등록한다.

   ```bash
   git push -u upstream HEAD
   ```

4. GitHub에서 base를 `main`, compare를 해당 `feature/*`로 지정해 PR을 만든다. PR에는 변경 목적, 확인한 항목, 미확인 항목을 적는다.
5. CI 정적 검사와 필요한 플레이 확인을 검토한 뒤 **merge commit**으로 `main`에 병합한다. 병합된 feature 브랜치는 GitHub에서 자동 삭제하며 `main`은 삭제 보호로 유지한다.
6. `main`을 갱신하고 병합된 로컬 feature 브랜치를 정리한다.

   ```bash
   git fetch upstream --prune
   git switch main
   git pull --ff-only upstream main
   git branch -d feature/room-reconnect
   ```

PR 충돌은 feature 브랜치에 최신 `upstream/main`을 병합해 해결한다. `main`에서 직접 커밋하거나 다른 작업의 미커밋 변경을 함께 스테이징하지 않는다.

`main`에 병합되면 CI의 `verify` 성공 후 운영 배포가 실행된다. `main`에서 CI를 수동 실행한 경우에도 배포 조건을 만족한다. 배포 조건과 실행 절차는 [배포 가이드](apps/db/DEPLOY.md)를 따른다.

### GitHub 저장소 설정

- 기본 브랜치와 기능 PR의 base는 `main`이다.
- 모든 PR은 merge commit으로 병합한다. squash/rebase merge와 auto-merge는 비활성화한다. merge commit을 유지하므로 linear history를 요구하지 않는다.
- `main`에는 활성 Ruleset을 적용한다. PR, `verify`·`rust`·`pr-flow` 성공, 리뷰 대화 해결을 요구한다. 승인 인원은 0명이며 관리자 우회도 허용하지 않는다. 강제 push와 브랜치 삭제는 금지한다.
- `feature/*`는 직접 push할 수 있다. 병합된 브랜치 자동 삭제를 사용한다.
- [PR 경로 검사](.github/workflows/pr-flow.yml)는 `feature/* → main`만 허용한다. PR 대상이 변경되어도 다시 검사한다.
- [PR 템플릿](.github/PULL_REQUEST_TEMPLATE.md)에 작업 목적, 변경사항, 정적 확인, 플레이 확인·미확인 항목을 기록한다.

### CI와 운영 배포 범위

- [CI](.github/workflows/ci.yml)와 [Rust 정적 검사](.github/workflows/rust.yml)는 `main`, `feature/*` push와 `main` 대상 PR에서 실행한다.
- 운영 배포 조건은 `main`의 push 또는 `main`에서 CI 수동 실행이다.
- CI 성공은 정적 검사·빌드 결과다. 실제 플레이 확인과 모든 버튼 확인의 완료 근거로 사용하지 않는다.
- `pr-flow`는 PR 경로만 확인한다. 운영 배포는 `main`의 CI `verify` 성공 후에만 실행한다.

## 로컬 실행

Docker Desktop, Node.js 22와 pnpm 9.12.0을 준비한 뒤 저장소 루트에서 실행한다.

```bash
pnpm install --frozen-lockfile
pnpm dev:rust
```

브라우저 주소는 `http://localhost:3300/ko-KR`다. 실행기가 격리된 PostgreSQL·Redis, Rust API와 TypeScript 계산 워커를 준비하고 스키마 migration·ROM import 후 웹을 Rust 연결 모드로 실행한다. 기존 환경 파일을 복사하거나 운영 DB·Redis 설정을 바꿀 필요는 없다. 로컬 비밀번호와 워커 토큰은 Git 제외 경로 `output/rust-local/local.env`에 최초 생성하며 기존 파일과 볼륨은 유지한다.

웹에서 Ctrl+C 후 `pnpm dev:rust:stop`으로 로컬 컨테이너를 중지한다. 다른 체크아웃이 이미 3300·3011을 쓰고 있으면 `RUST_LOCAL_PROJECT=poke-lounge-rust-local-2 RUST_LOCAL_WEB_PORT=3400 RUST_LOCAL_API_PORT=3012 RUST_LOCAL_DB_PORT=35433 RUST_LOCAL_REDIS_PORT=36380 pnpm dev:rust`처럼 프로젝트명과 포트를 바꿔 나란히 띄울 수 있다(볼륨은 프로젝트별로 분리되며, 중지할 때도 같은 변수를 준다). 세부 주소·생성 파일·재실행 주의사항은 [Rust 백엔드 문서](apps/api-rust/README.md#로컬-실행)를 따른다.

Rust 게임의 개발 절차는 `pnpm dev:rust`뿐이다. 운영 구성의 Docker 실행과 배포·DB 변경 주의사항은 [배포 가이드](apps/db/DEPLOY.md)를 따른다.

## 플레이어 테스트와 개발 확인

테스트는 실제 브라우저의 화면을 보고 플레이어처럼 한 동작씩 조작하는 방식만 허용한다. 기준은 [플레이어 직접 조작 지침](PLAYER_TESTING.md)이다. 기본 도구는 `agent-browser`이며 기존 `pnpm player:browser`는 로컬 HTTP용 대안이다. Playwright는 브라우저 API로만 사용한다. 자동 E2E·단위/API/통합 실행기와 Storybook 실행 환경은 제거했다. fixture·게임 상태 주입을 통한 검증은 금지한다.

모든 버튼 확인 요청에서는 화면·버튼·조건별 미검증이 남으면 전체 완료/PASS로 보고하지 않는다. 3라운드 최종 결과와 UI 퇴장까지가 전체 한 회이며 우승 여부는 조건이 아니다.

다음은 테스트가 아닌 빌드·정적 개발 확인이다. CI도 이 범위만 실행하며 성공을 플레이어 테스트 PASS로 해석하지 않는다.

```sh
pnpm lint
pnpm build
pnpm type:check:web
```
