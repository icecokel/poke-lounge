# Poke Lounge 플레이어 E2E 테스트 시나리오

확인 기준일: 2026-08-31
구현 대조 기준: working tree (`97ef44c3965a46d4adc8e6bd83f1aea294c9b70` 기반)

## 1. 목적

이 문서는 Poke Lounge 멀티플레이와 개인 성장 흐름의 E2E 인수 테스트 기준이다. 제품 규칙 자체는
[Poke Lounge 게임 규칙 인덱스](./poke-lounge-rules/index.md)에서 관리한다.

실행한 범위에 속한 모든 `P0` 시나리오를 통과해야 해당 기능을 정상으로 판정한다. 공개
멀티플레이와 개인 성장의 세부 판정은 규칙 인덱스와 연결된 하위 문서를 따른다. 8·9인 정원,
오류·재접속과 개인 성장 결과는 독립 시나리오이며 5인+AI 3명 한 사이클의 필수 단계가 아니다.

각 플레이어의 최종 목적은 3라운드 누적 점수 1위로 우승하는 것이다. E2E는 최초 플레이어의
서버 방 자동 생성, 후속 플레이어의 같은 방 자동 참가, 각자의 탐색·육성·전투, 최종 우승자
확정까지 하나의 경쟁 흐름으로 검증한다.

이 문서에서 **한 사이클**은 새 임시 비밀번호의 사람 5인 room에서 방 생성·순차 참가하고 시작
시 AI 3명이 자동 참가한 뒤 shared world, 3개 게임 라운드, 최종 순위·우승자 수렴, 사람 전원의
UI leave와 room `closed`까지 한 번 진행하는 실행이다. **반복 검증**은 완전히 정리된 독립 한
사이클을 새 임시 비밀번호로 다시 수행하는 상위 절차다.

### 1.1 기본 테스트 원칙

1. 플레이어마다 독립된 browser context와 저장 상태를 사용한다.
2. 각 플레이어의 실행 환경은 seed를 사용해 Desktop Web 또는 Mobile Web으로 무작위 배정한다.
3. 한 시나리오는 방 생성·참가, 준비, 플레이, 승부, 복구 중 하나의 사용자 관찰 결과를
   중심으로 검증한다.
4. 환경 seed, 파티와 행동 순서를 기록해 실행 입력을 재현한다. 전투 RNG 결과는 실행마다 달라질
   수 있으므로 우승자 자체를 고정하지 않고 각 실행 안에서 모든 화면이 서버 판정에 수렴하는지
   확인한다.
5. 임의 대기 시간보다 서버 시각, room snapshot과 화면 상태 전환을 기준으로 기다린다.
6. 주요 상태 전환과 최종 우승 화면을 캡처한다. 실패 시 공통으로 screenshot, console·page
   error와 민감값을 제거한 network metadata를 남기고, trace와 video는 Playwright scripted
   regression에서만 남긴다.
7. 임시 비밀번호, session ID, token과 cookie는 캡처나 로그에 노출하지 않는다.

## 2. 제품 계약

테스트는 [플레이와 성장 규칙](./poke-lounge-rules/play-and-growth.md),
[전투 규칙](./poke-lounge-rules/battle-rules.md),
[멀티플레이 규칙](./poke-lounge-rules/multiplayer-rules.md)과
[3라운드 챔피언십 규칙](./poke-lounge-rules/three-round-championship.md)의 사용자 관찰 결과를
검증한다. 이 문서에는 규칙을 다시 정의하지 않고 테스트 환경, 절차와 증적만 기록한다.

이 문서에서 방 생성은 최초 플레이어의 `create-or-join` 요청으로 서버 room이 생성되는 동작을,
방 참가는 같은 임시 비밀번호를 입력한 후속 플레이어가 해당 room에 자동 합류하는 동작을
뜻한다. 첫 화면은 방 만들기 화면이며 혼자 플레이 진입은 제공하지 않는다. 사용자는 닉네임과
임시 비밀번호를 제출한다. 공개 범위 선택에는 `공개`와 `비공개`가 표시되지만 현재 `공개`는
비활성화되고 `비공개`만 선택된다.

### 2.1 테스트 제외 범위

다음 항목은 공개 멀티플레이 인수 테스트에서 제외한다.

- Google 로그인, 계정 선택과 OAuth callback
- 사용자에게 보이는 방 코드, 방 생성·참가 선택과 초대 링크
- 방장 강퇴·방 설정, 준비 시간 선택과 경쟁 모드 설정
- Google 계정에 바인딩하는 competitive seat
- direct room URL, 수동 WebRTC와 내부 경쟁 API
- 사용자 간 파티·재화·인벤토리 공유

공통 셸이 `/api/auth/session`을 조회할 수는 있지만, 멀티플레이 접속 성공 조건으로 로그인이나
Authorization header를 요구해서는 안 된다.

## 4. 테스트 환경

### 4.1 환경 계층

| 환경      | Web           | API           | 관계형 DB          | 권위 room 상태 | 목적                       |
| --------- | ------------- | ------------- | ------------------ | -------------- | -------------------------- |
| UI 격리   | 로컬 Next.js  | 응답 fixture  | 없음               | 없음           | 입력·오류·레이아웃         |
| 로컬 통합 | 로컬 Next.js  | 실제 NestJS   | 테스트 준비·ROM DB | 격리 Redis     | 참가·Socket·leave·재접속   |
| 운영 인수 | 운영 배포 Web | 운영 배포 API | 운영 정책          | 운영 Redis     | 실제 배포·CORS·Socket·화면 |

계정·ROM 데이터 준비에는 관계형 DB를 사용할 수 있지만 room·match·action·tournament의 권위
상태 저장소는 Redis다.

운영 인수 테스트는 임시 비밀번호 원문, 쿠키, token과 전체 Socket payload를 artifact에 저장하지
않는다. 운영 room에는 테스트 전용 닉네임 prefix를 사용하고 완료 후 모든 참가자가 명시적으로
나간다.

### 4.2 브라우저 구성

| 환경          | 기본 viewport        | 입력   | 브라우저 매트릭스          |
| ------------- | -------------------- | ------ | -------------------------- |
| `Desktop Web` | 1440×900             | 키보드 | Chromium, P2 WebKit        |
| `Mobile Web`  | Pixel 7 기준 390×844 | 터치   | Chromium, P2 Mobile WebKit |

플레이어 역할은 `MP1`부터 `MP9`까지 유지하되 환경은 고정하지 않는다. 실행 시작 시 seed로 환경
목록을 섞어 각 플레이어에게 배정하고, 해당 실행이 끝날 때까지 같은 환경을 유지한다.

`agent-browser` 에이전트 실행에서 `Mobile Web`은 viewport만 줄이지 않고 방 입장 전에
`open --init-script .agents/skills/poke-lounge-agent-browser-test/scripts/mobile-touch-init.js`로 빈 named
session을 시작하고 `set device "iPhone 12"`를 적용한 뒤 대상 URL을 연다. `agent-browser` 0.34.0의
device preset이 적용하지 않는 touch capability만 리포지토리에서 검토한 init script로 보정한다.
viewport `390×844`와 `navigator.maxTouchPoints > 0`을 확인한 뒤에만 `ENV-READY`를 보고한다. `Desktop Web`은
`set viewport 1440 900`을 적용하고 touch device를 에뮬레이션하지 않는다. `필드 조작` deck과 터치
방향 패드는 라운드 시작 후 `C1-WORLD`에서 확인하며, 그때 없으면 `CODE-FAIL`이다.

- 2인 시나리오: `Desktop Web` 1개와 `Mobile Web` 1개를 섞어 배정한다.
- 5인+AI 3명 한 사이클: `Desktop Chromium` 2개와 `Mobile Chromium` 3개를 사람 플레이어에게
  섞어 배정한다.
- 8·9인 시나리오: `Desktop Web` 5개와 `Mobile Web` 4개를 섞어 배정한다.
- 실행 seed와 `MP 역할 → 환경` 배정 결과를 artifact에 기록하고 같은 seed로 재현할 수 있어야
  한다.

5인 실행의 배정은 실행마다 새 무작위 seed를 만들고 `SHA-256("<seed>|<MP 역할>")` 오름차순으로
역할을 정렬한 뒤 `Desktop Chromium` 2개, `Mobile Chromium` 3개 순서로 할당한다. 환경 선택은
무작위지만 seed와 계산식으로 재현 가능해야 한다. WebKit은 P2 scripted regression에서만 확인하고
agent-operated 한 사이클에는 배정하지 않는다.

모든 격리 context는 서로 다른 `localStorage`와 `sessionStorage`를 사용한다. 같은 사용자 재접속
시나리오에서만 기존 브라우저 프로필의 storage를 유지한다.

### 4.3 테스트 데이터

- `PW_A`: 실행 시 생성한 동일 세션용 임시 비밀번호
- `PW_B`: `PW_A`와 다른 격리 확인용 임시 비밀번호
- 닉네임: `MP-1`부터 `MP-9`
- 환경 배정: 실행 seed로 결정한 Desktop Web 또는 Mobile Web
- 저장 상태: 최초 실행은 빈 상태, 독립 진행 검증에서는 `MP1`만 파티·재화 fixture 보유
- 새 플레이어의 기본 지갑은 `₽0`, 기본 인벤토리는 몬스터볼 10개다.
- 성공 구매는 실행 중 storage/API로 돈을 주입하지 않고 앞선 야생전 보상 또는 실행 전에 준비한
  저장 진행으로 구매 가격 이상의 금액을 확보한 뒤 검증한다.
- 야생전 승리·도망·포획·패배는 서로의 HP·인벤토리·RNG 결과가 섞이지 않도록 독립 저장 상태로
  실행한다.

### 4.4 5인+AI 3명 한 사이클 공통 fixture

| 항목      | 기준                                                                                                                            |
| --------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 참가 순서 | `MP1` 방 자동 생성 완료 보고 뒤 `MP2`~`MP5` 순차 참가                                                                           |
| 자동 충원 | 방장 시작과 같은 Redis 변경에서 AI 3명이 추가되어 시작 snapshot부터 총 8명이 된다.                                              |
| 대진 seed | 사람은 참가 순서대로 1~~5, 자동 AI는 6~~8이며 8강은 `1-8`, `4-5`, `3-6`, `2-7`로 진행한다.                                      |
| 스타터    | 첫 실행은 각자 첫 번째 스타터, 반복 검증은 앞 실행에서 저장한 같은 파티                                                         |
| 전투 행동 | 매 턴 첫 번째 사용 가능한 공격 기술, 강제 교체 시 첫 번째 생존 슬롯                                                             |
| Desktop   | fresh `Poke Lounge 게임 화면` ref focus → 기본 선택 `싸운다` 확인 → Enter → fresh ref로 `move-select` 확인 → 첫 공격 기술 Enter |
| Mobile    | 화면의 `싸운다` touch → 기술 목록 확인 → 첫 공격 기술 touch                                                                     |
| 턴 시한   | 서버 turn 진입부터 30,000ms, 미제출자는 해당 턴 행동만 생략                                                                     |
| 결과 확인 | terminal 캡처 뒤 Desktop은 Enter, Mobile은 화면의 `다음`을 한 번 입력                                                           |
| 금지 행동 | 기권이나 브라우저 종료로 승패 유도                                                                                              |
| 준비 시간 | 분산 테스터는 제품 기본값 180,000ms, 단일 자동화만 90,000ms 허용                                                                |
| 승패 판정 | 실행마다 서버가 확정한 점수·순위·우승자와 사람 다섯 화면이 같은지 확인                                                          |

전투 참가자는 공유 관리자 채널에
`ACTION-ARMED <gameRound> <matchId> <turn> <MP 역할>`을 보낸다. 관리자는 같은 match·turn의 두
보고를 확인한 뒤 `ACTION-GO <gameRound> <matchId> <turn>`을 한 번 보낸다. turn 0만 이 시작 신호를
사용하고 이후 turn은 서버의 `command` phase와 turn 증가를 각 runner가 직접 감시해 진행한다.
`<matchId>`에는 authoritative competitive projection의 UUID `matchId`만 사용하고
`bracketMatchId`는 사용하지 않는다. 사람끼리 만난 매치의 두 사람이 보고 대상이며, AI가 포함된
매치는 사람 참가자만 보고하고 AI 행동은 서버 worker가 제출한다.

90초 준비는 모든 watcher와 입력 루프를 시작 전에 대기시킬 수 있는 단일 자동화 runner 전용이다.
독립 서브에이전트나 수동 테스터가 각자 브라우저를 조작할 때는 제품 기본값 180초를 그대로
사용한다. 다섯 화면의 `startedAtMs`, `endsAtMs`가 같은지 확인하며, 단축 실행 결과로 3분 제품 계약을
대체하지 않는다.

로컬 분산 테스트의 다섯 플레이어는 공개 입장 URL에 `e2e=1`만 지정하고 같은 임시 비밀번호로
참가한다. 공개 생성 화면은 URL의 `roundMs`를 방 생성 요청에 전달하지 않으므로 분산 fixture에
`roundMs`를 사용하지 않는다. `MP1`의 방 생성 요청 body에는 `roundDurationMs`가 없어야 하고 서버
room의 `durationMs`는 기본값 `180000`이어야 한다.

### 4.5 Playwright scripted regression

단일 Playwright 자동화만 방 생성 POST를 가로채 `roundDurationMs: 90000`을 병합해 90초 fixture를
사용할 수 있다. route handler 참조를 보존하고 최초 생성 응답 직후 `finally`에서 제거한다. 다음
실행 시작 시 각 Playwright page에서 `page.unrouteAll({ behavior: "wait" })`을 호출해 이전 override가
새 room 생성에 적용되지 않게 한다. 실패 증적에는 screenshot, trace와 video를 포함한다.

### 4.6 agent-browser 분산 실행

`agent-browser`는 route/mock, `page.unrouteAll()`, `fetch`, `curl`과 request replay를 사용하지 않고
제품 기본 준비 시간 `180000ms`를 지킨다. 방 입장 전에 named session의 network log를 비우고,
화면과 read-only E2E snapshot에서 필요한 값만 새 객체로 골라 읽는다. 전체 game/room snapshot을
반환하거나 저장하지 않는다.

```sh
agent-browser --session <name> eval --json "(() => { const c=window.__POKE_LOUNGE_E2E__; const s=c?.getGameStateSnapshot(); const b=c?.getBattleSnapshot(); return { connectionStatus:s?.session.connectionStatus ?? null, round:s ? { phase:s.round.phase, roundIndex:s.round.roundIndex, durationMs:s.round.preparationDurationMs, startedAtMs:s.round.phaseStartedAtMs, endsAtMs:s.round.preparationEndsAtMs } : null, competitive:b?.competitive ? { matchId:b.competitive.matchId, currentTurn:b.competitive.currentTurn, status:b.competitive.status } : null }; })()"
```

`network requests`는 method·status·민감 segment를 제거한 path와 건수만 증적으로 남긴다. 전체
request/response body를 출력하는 `network request <id>`는 실행하지 않는다.
필수 서버 필드를 whitelist 형태로 안전하게 읽을 수 없으면 raw body를 저장하는 대신 해당
checkpoint를 `DOC-GAP`으로 중단하고 Playwright scripted regression으로 넘긴다. 상태가 누락되거나
오래됐으면 60초 재접속 유예 안에 UI reload를 정확히 한 번 수행하고 화면과 whitelist snapshot을
다시 읽는다.

`PW_A`, `PW_B` 원문은 문서, URL, screenshot, trace 제목과 JSON 결과에 기록하지 않는다.
해시에서 파생된 내부 6자리 key도 사용자 화면 증거로 사용하지 않는다.

### 5.7 아이템 구매

구매 성공은 server mutation이 아니라 현재 플레이어의 `gameStateStore`가 지갑과 인벤토리에 함께

## 6. 실행 시나리오

### 6.1 agent-browser 분산 실행 오케스트레이션

| 실행 주체                  | 책임                                                                | 금지 사항                                     |
| -------------------------- | ------------------------------------------------------------------- | --------------------------------------------- |
| 루트 오케스트레이터        | 실행 준비, 환경 배정, 단계 동기화, 장애 분류, 증적 취합과 최종 보고 | 방 참가, 플레이어 입력과 승패 개입            |
| agent-browser runner 1~3개 | 배정된 독립 context의 입장·이동·전투·캡처와 상태 보고               | 다른 runner의 context 조작, 서버 판정 우회    |
| `MP` 플레이어 context      | 하나의 `playerId + sessionId`, 저장 상태와 Desktop·Mobile 환경 유지 | 다른 플레이어와 storage·cookie·입력 상태 공유 |

1. 루트 오케스트레이터는 browser를 열기 전에 실행 ID와 환경 seed를 만들고 `MP` 역할, runner,
   Desktop Web 또는 Mobile Web 환경을 무작위로 연결한다. 배정 결과는 같은 seed로 재현할 수 있게
   기록한다.
2. agent-browser runner 1~3개를 구성하고 환경 seed로 Desktop Chromium 1개와 Mobile Chromium
   2개를 섞어 배정한다. 한 runner가 여러 named session을 소유할 수 있지만 플레이어별 session,
   storage와 입력은 격리하며 루트는 플레이어가 되지 않는다.
3. 각 runner는 배정된 context에서 Poke Lounge 입장 화면을 연 직후 배정된 viewport와 Mobile touch
   emulation을 확인하고 named session의 network log를 비운 뒤 `ENV-READY`를 보고한다. 공개 입장
   화면과 waiting 대기실에는 설정 control이 없다. 방장이 시작해 대기실이 닫히면 각 runner는
   shortcut 또는 Mobile guide를 canonical control로 먼저 닫고, 이동·전투 입력 전에 설정을 즉시
   연다. 소리 control을 `소리 꺼짐`으로 맞추고 접근성 이름이 `소리 음소거`인지 확인한 뒤 설정을
   닫는다. 이미 꺼져 있으면 추가로 누르지 않는다. 완료한 플레이어마다
   `AUDIO-MUTED <MP 역할>`을 보고한다.
4. `MP1` runner가 최초 접속과 자동 방 생성을 담당하는 방장이다. 루트 오케스트레이터를 `MP1`,
   방장 또는 플레이어 슬롯으로 계산하지 않는다.
5. 루트는 `ENV-READY` 보고를 모두 받은 뒤 `MP1`에게 방 생성을 지시하고, `C0-HOST`를 확인한 뒤
   후속 참가를 순서대로 허용한다. ready·시작·대진 전환은 해당 checkpoint의 전원 보고가 모인
   뒤에만 다음 단계로 진행한다. 시작 뒤에는 전원의 `AUDIO-MUTED`와 이동 증적이 모두 모여야
   `C1-WORLD`를 통과시킨다.
6. 전투 첫 turn은 두 참가자의 `ACTION-ARMED`를 대조한 뒤 루트가 같은 `matchId`와 turn의
   `ACTION-GO`를 한 번 보낸다. 이후 turn은 각 runner가 서버 phase와 turn 전진을 따라 진행하며
   루트가 플레이 입력을 대신하지 않는다.
7. 전체 실행에는 별도 종료 시간 제한을 두지 않고 서버가 3라운드 누적 우승자를 확정할 때까지
   한 사이클을 진행한다. 제품의 준비 시간, turn deadline과 재접속 유예는 그대로 지킨다.
8. 각 runner는 필수 checkpoint를 캡처하고, 연결 복구 시나리오를 실제 수행한 경우에만 연결
   중단·REST 복구·Socket 재구독 전후 화면을 추가한다. 루트는 실행 ID, `MP` 역할, 환경,
   checkpoint와 시각을 대조하고 민감값을 제거한 증적만 취합한다.
9. runner가 `DOC-GAP`, `CODE-FAIL`, `TEST-RUNNER` 또는 `INFRA-BLOCKED`를 보고하면 루트가
   중단·재현·계속 여부를 결정한다. 내부 API로 행동이나 승패를 대신 만들지 않으며, 안전한
   checkpoint부터만 재개한다.
10. 루트는 중간 진행을 결과 보고로 간주하지 않는다. 우승자 확정과 room 정리가 끝난 뒤 환경별
    성공 여부, 최종 순위, 실행한 경우의 연결 복구 결과, 캡처와 결함만 하나의 최종 보고로 전달한다.

### 6.2 기본 2인 shared world

1. `MP1`, `MP2`의 storage를 비우고 Poke Lounge 입장 화면을 연다.
2. seed로 `MP1`, `MP2`의 환경을 배정하고 Desktop Web과 Mobile Web 입장 화면을 각각 캡처한다.
3. 두 context가 서로 다른 닉네임과 같은 `PW_A`로 비공개 방을 만들거나 참가한다.
4. 양쪽 대기실에서 두 닉네임, `MP1` 방장 표시와 준비 전 상태를 확인한다.
5. 두 사용자가 ready를 선택하고 방장 `MP1`이 시작한다.
6. 양쪽에 같은 3분 준비가 시작된 뒤 대기실이 닫히는지 확인한다.
7. 각 플레이어가 배정된 환경의 키보드 또는 터치로 이동하고 상대 화면의 좌표·방향 변화를
   확인한다.
8. `MP1`만 야생전에 진입한 동안 `MP2`가 계속 월드를 이동하는지 확인한다.
9. `MP1`의 전투 보상과 파티 변경이 `MP2`에 반영되지 않는지 확인한다.
10. 두 사용자가 방에서 나가고 입장 화면으로 돌아오는지 확인한다.

### 6.3 8명 정원·9번째 거부·재입장

1. `MP1`~`MP8`이 같은 `PW_A`로 비공개 방에 순서대로 접속한다.
2. REST snapshot에서 참가자 8명과 서로 다른 identity를 확인한다.
3. `MP9`이 같은 `PW_A`로 접속해 409 정원 초과 화면을 확인한다.
4. 정원이 찬 상태에서 `MP1`을 새로고침해 동일 identity와 참가자 8명을 확인한다.
5. `MP8`이 명시적으로 나가고 `MP9`이 다시 접속해 여덟 번째 자리를 얻는지 확인한다.
6. 한 참가자의 Socket을 일시 중단하고 60초 안에 재연결해 같은 자리를 유지하는지 확인한다.
7. 다시 연결을 끊고 유예를 넘겨 참가자 제거와 다음 신규 참가자의 입장을 확인한다.
8. 남은 모든 참가자가 명시적으로 나가도록 정리한다.

### 6.4 기본 2인+AI 2명 챔피언십

1. `MP1`, `MP2`가 같은 `PW_A`의 비공개 방에 접속해 각자의 파티를 준비한다.
2. 자동 party snapshot 뒤에도 대기실과 준비 전 상태가 유지되는지 확인한다.
3. 두 사용자가 ready를 선택하고 방장 `MP1`이 시작한다. 시작 snapshot부터 AI 2명이 추가되어
   4인 준비와 `4강 → 결승` 대진이 된다.
4. 양쪽 HUD의 현재 라운드와 남은 시간이 같은 서버 종료 시각을 기준으로 감소하는지 확인한다.
5. 각 플레이어가 우승을 목표로 합법적인 전투 행동을 제출하고 양쪽에 같은 전투 상태가
   표시되는지 확인한다.
6. 고정된 행동 순서로 첫 대진을 끝내고 terminal HP 비율 점수와 다음 대진 또는 다음 라운드
   전환을 확인한다.
7. 2·3라운드 준비가 별도 ready 없이 자동 시작되는지 확인한다.
8. 3라운드 완료 뒤 모든 화면에 같은 누적 최종 순위와 예상 우승자가 표시되는지 확인한다.
9. 최고 누적 점수가 같을 때는 공동 우승으로 표시되는지 별도 fixture로 확인한다.

### 6.5 개인 성장: 구매·야생전 결과

각 case는 독립 저장 상태와 새 room에서 수행한다. `MP1`은 실제 UI만 사용하고 `MP2`는 월드에
남아 자신의 파티·지갑·인벤토리 기준값을 유지한다.

1. 각 case 전 `MP1`의 좌표, 파티 HP·PP, 지갑, 몬스터볼 수량과 `MP2`의 같은 항목을 기록한다.
2. 승리 case에서 `MP1`이 야생전을 끝내 경험치·돈과 원래 좌표 복귀를 확인한다.
3. 승리 보상으로 `W >= ₽200`이 되면 기본 상점에서 몬스터볼 1개를 구매하고 `W-200`, `Q+1`,
   성공 문구를 확인한다. 금액이 부족하면 다른 합법적인 야생전 보상으로 충당하며 상태를 직접
   주입하지 않는다.
4. 도망 case는 새 저장 상태에서 시작한다. 실패한 시도마다 상대 행동과 피해를 확인하고 성공
   뒤 보상 없이 원래 좌표로 돌아오는지 확인한다.
5. 포획 case는 새 저장 상태에서 상대 HP를 낮추고 보유한 볼을 사용한다. 실패할 때마다 볼 1개
   차감과 상대 행동을 확인하며 성공 뒤 파티 또는 PC 박스 배치, 포획 보상과 원래 좌표 복귀를
   확인한다.
6. 패배 case는 새 저장 상태에서 파티 전멸까지 진행하고 보상 없이 전투불능 상태를 보존한 채
   필드 회복 지점으로 돌아가는지 확인한다. 간호사와 상호작용하기 전 자동 회복되면 실패다.
7. 각 case 뒤 `MP2`의 파티·지갑·인벤토리가 기준값과 같은지 확인하고 두 참가자가 UI로 나간다.

로컬 scripted regression은 지원되는 `wild-victory`, `wild-defeat` fixture와 seeded battle logic
테스트를 사용할 수 있다. agent-operated public-UI 실행은 결과를 만들기 위해 E2E controller나
내부 API를 호출하지 않는다.

### 6.6 5인+AI 3명 shared world·3라운드 챔피언십 한 사이클

#### 실행 전

1. 관리자는 격리 DB와 실제 API·Web을 준비하고 실행 ID, 환경 배정 seed, 임시 비밀번호와 artifact
   경로를 만든다. 관리자는 플레이어 context를 조작하지 않는다.
2. Playwright page를 사용하는 scripted run에서만 이전 route를 `page.unrouteAll({ behavior:
"wait" })`로 제거한다. 단일 자동화의 90초 생성 override는 handler 참조를 보존하고 생성 응답
   직후 `finally`에서도 제거한다. agent-browser runner는 route를 다루지 않고 각 named session의
   network log만 비운다.
3. 다섯 플레이어는 이 문서와 연결된 멀티플레이·챔피언십·전투 규칙을 읽고 자신의 환경, 입력,
   참가 순서와 캡처 목록을 관리자에게 확인 보고한다.
4. 이번 실행에서 문서만으로 다음 행동이나 기대 결과를 결정할 수 없으면 브라우저를 시작하지
   않고 `DOC-GAP`으로 중단한다. 관리자가 문서를 개정한 뒤 다섯 플레이어 모두 처음부터 다시
   읽는다.

#### C0 방 생성·순차 참가

1. `MP1`만 입장 화면을 열어 멀티플레이 탭을 선택하고 닉네임과 `PW_A`를 제출한다. 자동 방 생성
   뒤 스타터 선택 화면이 열리면 첫 번째 스타터를 확정하고 party snapshot 동기화가 끝날 때까지
   기다린다.
2. 분산 실행에서는 방 생성 요청 body에 `roundDurationMs`가 없고 서버 room의 `durationMs`가
   `180000`인지 확인한다. 단일 자동화에서는 요청과 서버 값이 모두 `90000`인지 확인한다. 이전
   route 값이 남아 기준과 다르면 제품 assertion 전에 중단·정리하고 `INFRA-BLOCKED`로 보고한다.
3. `MP1`은 대기실에서 자신이 유일한 참가자이자 방장이고 파티 동기화가 완료됐음을 캡처한 뒤
   관리자에게 `C0-HOST`를 보고한다.
4. 관리자 승인 뒤 `MP2`부터 `MP5`까지 서로 다른 context에서 멀티플레이 탭을 선택하고
   닉네임과 같은 `PW_A`를 제출한다. 각자 스타터 선택 화면에서 첫 번째 스타터를 확정하고 자신의
   party snapshot 동기화 완료를 보고한 뒤에만 다음 플레이어가 참가한다.
5. 각 참가자는 다섯 닉네임, `MP1` 방장, 다섯 파티 동기화 완료, 모두 준비 전, 타이머 미시작을 자기
   화면에서 확인하고 `C0-JOINED`를 보고한다.

#### C1 ready·수동 시작·shared world

1. `MP2`부터 `MP5`, 마지막으로 `MP1` 순서로 ready를 선택한다. 일부만 ready일 때 시작 버튼이 비활성인지,
   전원 ready 뒤 `MP1`에게만 활성인지 캡처한다.
2. 비방장 네 플레이어가 전환 watcher와 4의 이동 절차 준비를, `MP1`이 시작 직후 이동 연속 절차
   준비를 보고한 뒤 `MP1`이 시작한다. 같은 시작 snapshot에 자동 AI 3명과 각 starter party가
   추가되어 참가자가 8명인지 확인한다. 다섯 화면의 `startedAtMs`, `endsAtMs`, 라운드 번호가
   같은지 확인한다.
3. `waiting` 대기실에서는 이동할 수 없어야 한다. 시작 후 `round-started` 준비 단계에서는
   대기실이 닫히고 각자 월드를 탐색할 수 있어야 한다.
4. Mobile은 `필드 조작` deck이 열려 있으면 접근성 이름 `뒤로` control로 먼저 닫고
   `shortcutGuideOpen=false`, world-help 제거, explore deck과 joystick 표시를 확인한다. Desktop도
   shortcut guide가 열려 있으면 `Escape`를 정확히 한 번 입력해 `shortcutGuideOpen=false`와 help UI
   제거를 확인한다. guide를 닫은 뒤 설정을 열어 소리 control을 `소리 꺼짐`으로 맞추고 접근성 이름
   `소리 음소거`를 확인한 뒤 설정을 닫아 `AUDIO-MUTED`를 보고한다. 입력 전 화면 경계·장애물을 피한
   이동 가능 방향 중 현재 avatar가 바라보는 방향과 다른 방향을 고른다. Desktop은 game surface focus 뒤
   `node .agents/skills/poke-lounge-agent-browser-test/scripts/desktop-arrow-hold.mjs <session> <Arrow>`를 한 번
   실행한다. 이 helper는 공식 `agent-browser` stream 입력으로 물리 방향키 code를 포함한 keyDown을 보내고
   50ms 뒤 같은 키의 keyUp을 보장한다. `agent-browser` 0.34.0의 CLI `keydown`은 방향키의 물리 code를
   보내지 않으므로 사용하지 않고, 유지 시간이 없는 `press`도 이동에 사용하지 않는다. Mobile은 해당
   방향 control을 pointer-down해 active·방향 표시와 좌표 변화를 확인한 뒤 pointer-up한다. 고정된
   유지 시간을 통과 조건으로 삼지 않는다. 변화가 없을 때만 같은 방향으로 한 번 더 입력하고 다른
   화면에 avatar 좌표·방향이 반영되는지 확인한다. 경계·장애물 방향이나 현재 바라보는 방향을 골라
   좌표·방향 변화를 만들지 못하면 `TEST-RUNNER`로 중단한다. 각 runner는 자신의 시작 전환을 관찰하면
   다른 runner의 timing field나 이동
   보고를 기다리지 않고 이 절차까지 연속·병렬 수행한다. 루트는 전원 보고 뒤 timing field와 동기화
   증적을 대조한다. 준비 `endsAtMs` 전에 전원 checkpoint를 끝내지 못하면 `TEST-RUNNER`로 중단한다.
5. 준비 종료 5초 전에는 다섯 화면에 `8강 → 4강 → 결승`과 각자의 위치가 표시되고 부전승은 없으며,
   카운트다운 종료 뒤 별도 입력 없이 서버 경쟁 대진으로 전환되는지 확인한다.
6. 이동으로 야생전이 열리면 해당 화면을 캡처하되 파티 상태를 바꿀 수 있는 battle command를
   입력하지 않는다. 다른 플레이어의 world 진행이 유지되는지 확인하고 서버 경쟁 대진을
   기다린다. 참가자에게 competitive assignment가 생기면 로컬 야생전 대신 해당 전투가 열려야 한다.
   배정 뒤에도 야생전이 남으면
   `CODE-FAIL`이다.
7. 각 사람 참가자는 준비 `endsAtMs + 15000ms`까지 자신의 authoritative room projection에서
   UUID `competitive.matchId`와 server competitive battle scene 또는 입력 잠금 관전을 확인한다.
   제한 시간까지 배정이나 scene 전환이 없으면 민감값을 뺀 최신 room projection과 scene을
   캡처하고 `CODE-FAIL`로 중단한다.

#### C2 각 게임 라운드의 8인 대진

1. 준비 종료 뒤 다섯 화면과 서버 snapshot에서 `1-8`, `4-5`, `3-6`, `2-7`의 8강 네 경기와
   부전승 없음이 같은지 확인한다. 각 참가자는 자신의 경기 또는 입력 잠금 관전 Battle scene으로
   전환되고 준비 중 열린 로컬 야생전은 남지 않아야 한다.
2. 사람끼리 만난 매치는 두 참가자의 `ACTION-ARMED`를 대조한 뒤 같은 match·turn에
   `ACTION-GO`를 보낸다. AI가 포함된 매치는 사람 참가자만 화면으로 행동하고 AI 제출은 서버
   worker가 담당한다. 사람은 서버 turn 진입부터 30초 안에 행동한다.
3. Desktop은 fresh game surface를 focus하고 `싸운다` Enter 뒤 fresh ref에서 첫 기술 Enter를
   입력한다. Mobile은 `싸운다`와 첫 공격 기술을 차례로 touch한다. 강제 교체는 첫 생존 슬롯을
   선택하며 기권이나 브라우저 종료로 승패를 만들지 않는다.
4. 각 사람 입력은 5초 안에 `session-actions` 2xx가 발생해야 한다. 요청이 없으면 같은 UI 절차를
   한 번만 다시 수행하고, 두 번째에도 없거나 non-2xx이면 `CODE-FAIL`로 중단한다. AI 행동은
   browser 요청이 아니라 서버 projection의 제출·turn 전진으로 확인한다.
5. terminal 참가자는 결과 화면과 원시 terminal HP를 먼저 캡처한 뒤 결과 control을 정확히 한
   번 확인한다. 같은 UUID의 완료 증적은 action 응답, `competitiveTransitions` 또는 완료된 bracket
   history에서 확인하며 다음 대진 projection으로 이전 승패를 추론하지 않는다.
6. 각 8강이 끝난 뒤 4강 두 경기, 이어서 결승 한 경기가 생성되는지 확인한다. 탈락자와 다른
   대진 참가자는 같은 Battle scene을 입력 잠금 상태로 관전한다.
7. 결승 종료 뒤 다섯 화면에서 라운드 우승자, 참가자 8명의 확정 terminal HP 점수와 누적 순위를
   대조한다. 한 게임 라운드의 전체 매치는 7개여야 한다.
8. 1·2라운드 뒤에는 별도 ready 없이 사람 5명과 AI 3명이 모두 다음 준비에 포함되어야 한다.
9. 1~8을 게임 라운드 3까지 반복해 전체 21개 매치와 최종 누적 순위를 확인한다.

#### C3 최종 결과·정리

1. 다섯 화면의 3라운드 누적 점수, 순위와 최종 우승자가 서버 snapshot과 같은지 확인한다.
2. 이번 실행은 파티 snapshot, 행동 순서, 라운드별 승자·점수와 최종 우승자를 민감값 없이
   관찰 결과로 저장한다.
3. `MP5`부터 `MP1` 역순으로 한 명씩 정리한다. 같은 match의 결과를 아직 확인하지 않았고
   visible·enabled 결과 control이 있을 때만 C2의 결과 확인을 정확히 한 번 먼저 수행한다. 이미
   확인한 match의 cached `phase=ended` 또는 `result`만 남고 결과 control이 없으면 추가 키나 touch
   없이 leave 단계로 진행한다. Mobile world-help는 접근성 이름 `뒤로`, Desktop shortcut guide는
   `Escape`로 도움말을 닫은 뒤 메뉴를 열어 `방 나가기`가 표시되는지 확인한다.
   leave POST watcher를 먼저 설치하고 메뉴의 `방 나가기`를 한 번 입력한다. 즉시 POST가 발생하면 추가
   click을 금지하고, POST가 없으면서 confirm dialog가 표시될 때만 confirm의 leave를 한 번 입력한다.
   UI 활성화는 한 번만 하며 정상 경로의 leave POST도 한 번이다. revision conflict 또는 network
   오류에는 클라이언트가 최신 revision으로 한 번 재시도할 수 있지만 runner가 다시 누르지 않는다.
   최종 2xx와 `connected=false` 또는 참가자 제거가 반영된 뒤 다음 플레이어를 진행한다. 전원이 입장
   화면으로 돌아오고 room이 `closed`, 모든 참가자가 `connected=false`로 수렴하는지 확인한다.
   완료된 tournament의 audit 참가자 행은 남을 수 있으며 연결된 ghost 참가자로 판정하지 않는다.
   동시 leave 복구는 `MP-ERROR-008`에서 별도 검증한다.

### 6.7 반복 검증

반복 검증이 필요할 때만 완전히 정리된 한 사이클을 새 임시 비밀번호로 다시 실행한다. 같은 세
browser context의 저장 진행, seed, 환경 배정, 파티와 행동 순서를 보존하되 앞 room의 identity와
active-room 연결은 leave로 제거한다. 명중·급소·대미지 RNG로 승자와 점수는 달라질 수 있으므로
각 실행 안에서 다섯 화면과 서버 결과가 일치하는지를 판정한다. 두 번 연속 모든 runner가 문서 개정
불필요로 판정하면 반복 검증을 종료할 수 있지만, 이 조건은 단일 한 사이클의 통과 조건이 아니다.

#### 중단·분류 기준

- `DOC-GAP`: 절차, 환경, 대진, 행동, 기대 결과 또는 캡처 기준이 없거나 서로 모순된다. 즉시
  중단하고 브라우저·서버 상태와 문서 위치만 보고한다.
- `CODE-FAIL`: 문서와 제품 규칙의 기대 결과는 명확하지만 화면, API, Socket 또는 Redis 권위 상태가 다르게
  동작한다. 안전한 다음 checkpoint까지 증적을 보존한 뒤 관리자가 계속 여부를 정한다.
- `TEST-RUNNER`: `ACTION-GO` 전 입력, 2xx 뒤 같은 turn 재입력, Desktop battle의 stale ref 재사용·
  game surface focus용 click, 지정하지 않은 UI 입력 또는 서버 phase 전환 전에 필수 checkpoint를 끝내지
  못하거나 terminal 참가자를 다음 대진에서 추론한 경우처럼 runner가 절차를 위반했다. 제품 실패로
  세지 않고 새 입력을 즉시 중단해 증적을 보존한 뒤 room을 정리하고 같은 seed·환경 배정·파티·행동
  순서로 처음부터 다시 실행한다.
- `INFRA-BLOCKED`: 브라우저 실행 파일, 격리 DB, 포트 또는 서버 기동 문제로 제품 동작에 도달하지
  못했거나 이전 실행의 request route가 새 fixture를 오염시켰다. 제품 실패로 세지 않고 환경 로그를
  남긴다.

## 7. 필수 증적

아래 증적은 실행한 시나리오에 해당하는 항목만 필수다. 독립 시나리오의 증적을 5인+AI 한 사이클에
억지로 포함하지 않는다.

| 번호 | 증적                                                        |
| ---- | ----------------------------------------------------------- |
| `01` | 무작위 배정된 Desktop Web 입장 화면                         |
| `02` | 무작위 배정된 Mobile Web 390×844 입장 화면                  |
| `03` | 최초 플레이어 접속 뒤 자동 생성된 방과 방장 상태            |
| `04` | 후속 플레이어 자동 참가 뒤 양쪽의 동일 참가자 목록          |
| `05` | Mobile 대기실의 두 참가자와 준비 상태                       |
| `06` | 한 명만 ready인 상태의 비활성화된 시작 버튼                 |
| `07` | 전원 ready 뒤 방장에게만 활성화된 시작 버튼                 |
| `08` | 방장 시작 뒤 같은 준비 종료 시각이 표시된 양쪽 화면         |
| `09` | 여덟 참가자가 모두 들어온 대기실                            |
| `10` | 9번째 사용자의 8명 정원 초과 안내                           |
| `11` | 시작 뒤 신규 참가자의 접속 거부 안내                        |
| `12` | 대기실 방장 이탈 뒤 다음 참가자에게 권한이 승계된 상태      |
| `13` | 한 사용자는 야생전, 다른 사용자는 월드인 독립 상태          |
| `14` | 경쟁 매치 참가자와 입력 잠금 관전자의 같은 Battle scene     |
| `15` | 서버 확정 대진 결과와 terminal HP 라운드 점수               |
| `16` | 1·2라운드 종료 뒤 현재 누적 순위                            |
| `17` | 3라운드 누적 최종 순위와 우승자                             |
| `18` | 테스트 종료 후 입장 화면 또는 정리된 room 상태              |
| `19` | 상점 판매 목록과 구매 전·후 지갑·수량·성공 문구·재실행 복구 |
| `20` | 야생전 승리 결과, 경험치·돈, 전투 후 HP·PP와 원래 좌표      |
| `21` | 도주 실패의 상대 행동, 성공 결과, 무보상과 원래 좌표        |
| `22` | 포획의 볼 차감, 파티·PC 배치, 절반 보상과 원래 좌표         |
| `23` | 패배의 전멸 파티, 무보상, 회복 지점 좌표와 자동 회복 없음   |

5인+AI 3명 한 사이클은 아래 담당 플레이어가 checkpoint를 캡처한다. `전원` checkpoint는 다섯 화면에서
각각 남긴다.

| checkpoint           | 담당   | 필수 증적                                                              |
| -------------------- | ------ | ---------------------------------------------------------------------- |
| `C0-HOST`            | `MP1`  | `MP1` 한 명, 방장, 파티 동기화 완료, 준비 전인 자동 생성 대기실        |
| `C0-JOINED`          | 전원   | 다섯 닉네임, `MP1` 방장, 파티 동기화 완료, 전원 준비 전, 타이머 미시작 |
| `C1-PARTIAL-READY`   | `MP1`  | 일부만 ready인 상태와 비활성 시작 버튼                                 |
| `C1-ALL-READY`       | 전원   | 전원 ready와 `MP1`에게만 활성인 시작 버튼                              |
| `C1-WORLD`           | 전원   | AI 3명을 포함한 8명, 같은 준비 종료 시각과 환경별 이동 동기화          |
| `C2-BRACKET`         | 전원   | 부전승 없는 8강 네 경기와 `8강 → 4강 → 결승` 흐름                      |
| `C2-FIRST-ACTION`    | 참가자 | 사람 UI 입력과 AI 자동 제출, 2xx 또는 서버 상태 전진                   |
| `C2-FIRST-TERMINAL`  | 전원   | 첫 대진 승자, 원시 terminal HP 상태와 다음 대진                        |
| `C2-FIRST-CONFIRMED` | 전원   | 승자의 다음 battle, 탈락자의 입력 잠금 관전                            |
| `C2-ROUND-RESULT`    | 전원   | 결승 뒤 게임 라운드별 우승자, 참가자 8명 확정 점수와 누적 순위         |
| `C3-FINAL`           | 전원   | 다섯 화면의 같은 최종 순위와 우승자                                    |
| `C3-CLEANUP`         | 전원   | 순차 leave 성공, 입장 화면 복귀, room `closed`, 전원 `connected=false` |

각 screenshot은 시나리오 ID, browser, viewport와 시각을 함께 기록한다. 추가 JSON·로그에는 다음
중 실행 범위에 필요한 값만 남긴다.

- commit SHA와 배포 URL
- 실행 seed와 `MP` 역할별 Desktop Chromium 1개·Mobile Chromium 2개 배정 결과
- 공개 participant 수, host 역할과 room status
- 예상된 409 한 건과 `POKE_LOUNGE_ROOM_FULL` code
- 자동 party snapshot 여부, 수동 ready·start, session action 요청 경로와 competitive seat 요청 0건
- 다섯 화면의 준비 시작·종료 시각
- 역할별 참가 순서·seed·자동 AI·대진 승패·게임 라운드별 terminal HP 점수
- 전투 입력별 화면 phase, 실제 keyboard·touch 입력, `session-actions` 응답과 submitted 반영
- terminal 결과 확인 전·후 scene과 활성 참가·입력 잠금 관전 여부
- 구매 전·후 지갑·수량과 저장 복구 결과
- 야생전 결과별 HP·PP·지갑·볼·파티 또는 PC·복귀 좌표 변화
- console error, page error, 예상하지 않은 4xx/5xx와 가로 overflow 여부

임시 비밀번호 원문, 방 코드, `playerId`, `sessionId`, token, cookie, 전체 HTTP body와 전체 Socket
payload는 남기지 않는다.

## 8. 통과 기준

실행한 시나리오에 해당하는 기준을 모두 만족해야 통과다.

1. `MP1`~`MP8`은 대기실에 참가하고 `MP9`은 정원 초과로 거부된다.
2. 최초 참가자가 방장이며 명시적 이탈이나 60초 재접속 유예 만료 뒤 다음 참가자에게 승계된다.
3. party snapshot은 자동 동기화되지만 ready와 1라운드 준비는 자동 시작되지 않는다.
4. 방장은 혼자여도 파티 동기화와 ready를 마치면 시작할 수 있으며, 여러 명이면 모든 사람이
   ready일 때만 시작할 수 있다. 시작 시 1~~3명은 4명, 4~~7명은 8명까지 AI가 자동 참가한다.
5. 방장 시작 뒤 모든 참가자의 준비 시작·종료 시각이 같고 정확히 3분이다.
6. 시작 뒤 신규 참가자는 거부되고 기존 identity 재접속은 허용된다.
7. 준비 취소로 `waiting`에 돌아오면 ready를 해제하고 대기실을 다시 연다.
8. Desktop 키보드와 Mobile 터치 이동이 시작 이후 서로의 화면에 반영된다.
9. 각 사용자의 파티·재화·전투 진행은 다른 사용자에게 공유되지 않는다.
10. 임시 비밀번호 원문과 identity credential이 URL, 로그와 artifact에 노출되지 않는다.
11. 경쟁전은 competitive seat 없이 private session identity를 사용한다.
12. 3분 준비, 부전승 없는 4인 또는 8인 서버 권위 대진, terminal HP 점수와 3라운드 누적 순위가
    규칙대로 진행된다.
13. 경쟁 매치 비참가자는 같은 Battle scene을 입력 잠금 상태로 관전한다.
14. 정상 구매는 가격만큼 지갑이 줄고 아이템이 1개 늘며, 재실행 후에도 한 번만 반영된다.
15. 야생전 승리는 경험치·돈, 도주는 무보상, 포획은 볼 차감·포켓몬·절반 돈 보상, 패배는
    무보상·전멸 상태·회복 지점 복귀로 각각 반영된다.
16. 야생전 승리·도주·포획은 원래 좌표로, 패배만 회복 지점으로 돌아가며 패배 파티는 자동 회복하지 않는다.
17. 예상된 접속 거부 외에 예상하지 않은 4xx/5xx, page error와 console error가 없다.
18. Desktop과 Mobile에서 entry, 대기실, world, 전투, 챔피언십과 오류 화면이 frame을 벗어나지 않는다.
19. 5인+AI 3명 한 사이클은 세 라운드 21개 매치의 대진·점수·최종 우승자가 다섯 화면과 Redis
    권위 상태에서 같고,
    전원 UI leave 뒤 room이 `closed`로 수렴한다.
